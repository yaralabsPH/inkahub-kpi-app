# Frame timing implementation plan

Use executing-plans; actual Claude is sole app writer.
Goal: useful per-size/frame timing with measured scan gaps and explicitly labelled Max-method estimates.
Spec: docs/specs/frame-timing.md
Branch: feature/frame-timing, stacked on accepted reports-v2.
Architecture: reuse F8 authorized generation/filter contract and full frozen source_versions; server computes complete worker streams before filtering. Small pure TypeScript reference pins math; additive SQL returns bounded aggregates. Existing React primitives, no dependencies.

## Review focus

Multiple lines from one shared scan must not create zero gaps; filtered reports must retain whole-stream timing; measured time cannot be allocated again as estimates; absence of attendance/weights must be explicit; immutable configuration must not change old versions; staff cannot query team metrics; historical department is frozen snapshot.

## Staging / rollback

Root validates synthetic scan groups, clocked shift with partial measured/unmeasured work, missing weights, role denials and update conflict in an actual staging SQL rollback fixture. Hosted Preview verifies selection/labels and owner Settings, previous scans/stock are smoke-tested only where changed. Cleanup exact disposable fixtures, verify original stock/event hashes. Previous Preview and retained SQL give rollback. Never production. Deadline02:00UTC2026-11-23; incomplete is reported honestly.

## Implementation log

- Task 1: `src/lib/domain/frameTimingReport.ts` is the single timing engine (pure, run server-side): captures keyed by the strict `scn-<32hex>-vNN` request prefix (else one per event), per worker+production-day streams in time order, framing = effective `line_verified` with F1 `timing_weight` > 0 at framed/A0; clock events and any other effective verification break the chain; cancelled verifications are ignored; gaps 0 < g <= 30 min split by pieces; Max method per well-formed clock pair (shift) inside the day and not after the pinned cutoff: min(att,450)*405/450 minus that shift's measured minutes, clamped, split over unmeasured pieces x size weight; any missing weight makes the shift's allocation unavailable; filters applied only after timing. `0058_frame_timing.sql`: immutable `frame_timing_weight_versions` (RLS, no app-role table grants, update/delete trigger refuses), owner-only SECURITY DEFINER `read_frame_timing_weights` / `save_frame_timing_weights` (profiles role, site/size/value validation, advisory lock + expected-version conflict), service-only `read_frame_timing_rows` (checked_generation for the PINNED generation, sel_eval verifications + same-sequence source_versions department and clock images, row limit refused not truncated, 731 dates). `api/_lib/frame-timing.ts` reuses F8 `authorizeOverview` + `resolveGeneration(pinned)`. Ruling: the plan said SQL returns aggregates; I return bounded stream rows to the server and aggregate in the one TS engine, so SQL and TS cannot drift and the browser still only receives aggregates — cost if wrong: up to 50,000 rows per request between DB and function. Ruling: a "shift" is one clock-in/clock-out pair. Tests: `tests/production/frame-timing.test.ts` (15, spec examples) and `tests/reporting/pg/frame-timing.test.ts` (real SQL: shared capture, UN break, cancellation, pinned generation, roles, owner RPCs, conflict, immutability, estimates). `reportingJobs` numbering test expects 0057, 0058 last.
