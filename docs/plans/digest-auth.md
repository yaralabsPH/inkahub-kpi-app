# Plan: Authenticate daily KPI digest requests

- Slug: `digest-auth` · Spec: `docs/specs/digest-auth.md`
- Branch: `feature/digest-auth`
- Status: draft

## Approach

Protect the existing default handler in `api/reports/daily-digest.ts` with one entry sequence: set `Cache-Control: no-store`, authenticate, require GET, validate any explicit recipient override, then enter the existing diagnostic/report branches. Read configuration per request. Require a nonblank `CRON_SECRET` and exactly one bearer credential matching the original, untrimmed secret. A Supabase login, role, query parameter or claimed cron identity provides no alternative authorization. Keep report calculations, diagnostic payloads, location/date selection, XLSX generation and schedules unchanged.

Keep the small authorization/address helpers private in this handler; do not extract or rewrite report generation. Validate an explicit override before either diagnostic branch or any Supabase, fetch or XLSX work. Use the already-installed Zod email validator with explicit rejection of list delimiters, display-name syntax and embedded whitespace/control characters; trim surrounding address whitespace and lowercase for allowlist matching and override delivery. Default email delivery uses validated `REPORT_RECIPIENT` only. Check that default at the existing send boundary, after download/no-activity exits, so those operations still work without email configuration; move this check before `buildBodyText`. A valid allowlisted override supplies its own destination and does not require a configured default.

Add `tests/api/daily-digest.test.ts` outside the deployable `api/` tree and whitelist `/tests/` in `.gitignore`. Tests import the actual handler and mock Supabase, XLSX and global fetch; no production credentials, database or email service are used. Keep the existing local request/response interfaces and use `Parameters<typeof handler>` in the test harness. No dependency addition is needed: Vitest, TypeScript, Node types and Zod are already installed. Reuse those packages; leave `package-lock.json` unchanged.

`npx tsc -b` and the current build do not cover `api/`. Add a focused `typecheck:digest` package script and a CI step rather than expanding this feature into checking/fixing every server endpoint. Its exact command is `tsc --noEmit --strict --skipLibCheck --target ES2020 --module ESNext --moduleResolution bundler --types node api/reports/daily-digest.ts tests/api/daily-digest.test.ts`. This checks the changed handler and its tests without emitting files. Vitest remains part of the normal full test command. Neither repository adapter, `Repository.ts`, RLS nor the database schema changes.

### [ ] Task 2: Enforce recipient policy without breaking default delivery

- Files: modify `api/reports/daily-digest.ts`, `tests/api/daily-digest.test.ts`; update this plan's checkbox/log.
- Do: Add private `normalizeEmail(value: string): string | null` for a trimmed, lowercase individual address, rejecting malformed/list/display-name/control-character input. Use the installed `z.string().email().safeParse` with the extra single-address exclusions described in Approach. Add private `resolveRecipientOverride(raw: string | string[] | undefined, allowlist: string | undefined): { recipient?: string; error?: { status: 400 | 403 | 500; message: string } }`. An absent query value means no override; empty, malformed, repeated/array or multi-address values return `400` / `Invalid recipient`. Validate input first, then parse the comma-separated allowlist, trim entries and ignore blank entries. Any malformed nonblank entry fails the entire override configuration with `500` / `Recipient configuration error`, even if another entry matches. With a valid or absent list, require exact normalized full-address membership, otherwise `403` / `Recipient not allowed`. Reject wildcards, domain rules and suffix matching. Never fall back to the default on an override failure.
- Do: Call the override resolver immediately after the method guard, before diagnostics, location handling or report work. Return generic JSON errors without submitted values, credentials or allowlist contents. Use the resolved normalized address for an accepted override. When an email will actually be sent without an override, require `REPORT_RECIPIENT` to pass the same single-address validation; deliver to its trimmed configured value. Missing/blank/invalid default returns generic `500` / `Recipient configuration error` without sending. Delete the hardcoded fallback address. Default sends neither parse nor depend on the allowlist; diagnostics, downloads and unforced no-activity skips do not require a default destination.
- Done when: Handler tests prove an allowed address with whitespace/case variations sends to the normalized address, plus-addresses require exact membership, and an absent override sends to `REPORT_RECIPIENT` even with an absent/empty/malformed allowlist. Explicitly passing the default address still requires membership. Disallowed full addresses and suffix lookalikes give 403; empty/whitespace, invalid syntax, display names, commas/semicolons, newline injection and arrays give 400. Blank list entries are ignored, absent/empty lists deny overrides, and any nonblank malformed list entry gives 500 for otherwise valid override input. Exercise each override rejection with `dry`, both diagnostics, `force`, and an empty-activity fixture: assert zero Supabase/client calls, fetches and XLSX calls, plus no-store and generic bodies. Auth failure remains 401 even when input/configuration is invalid; authenticated non-GET remains 405 before recipient validation. Missing/invalid default prevents Resend calls on active/forced email requests; valid overrides work without a default; downloads/diagnostics/no-activity skips remain usable. Focused and full checks pass. Commit: `task 2: restrict digest recipient overrides and validate defaults`.
