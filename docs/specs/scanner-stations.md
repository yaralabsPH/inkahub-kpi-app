# F6: Shared scanner stations

Approved by Codex under CJ's autonomous overnight delegation, 2026-11-22. Staging only. Depends on F5; retains F4 and #10 Station. Actual scanner purchase/configuration and real packaging rules are commissioning requirements, not guesses to fill in tonight.

## Result and boundaries

An opt-in Shared scanners mode in the existing Production area accepts three cordless scanners. Each has its own active person. A valid order scan saves every eligible framing line for that person without taps. The classic station remains the fallback. Supabase-only is explicit, as for existing Production; do not change Repository or DexieRepo. Use existing Dexie dependency only for the device queue. Do not map managed business departments to work types; F5 captures membership independently in its database triggers.

Normal path: enable station once -> scan badge -> scan order -> green saved confirmation. Offline orders for an already active person show amber queued confirmation; green appears only after the server transaction succeeds. Storage failure, malformed input, expired identity or unsupported order is loud and visible. No pop-up before automatic badge sign-in. The page must not silently ignore a scan because another request is busy.

## Decisions

1. Strict frame `<S1>payload</S1>` plus Enter, similarly S2/S3, with configurable unique scanner IDs restricted to short safe ASCII. No substring recovery. Bound total frame length and inter-character/frame time; reject nested/mismatched/unknown markers, stray text and interleaved bursts. Corruption clears all scanner identities when the source is uncertain. Ignore setup/form typing while explicitly displaying that capture is paused. After a malformed burst, require a clean boundary before accepting a new frame. Test representative interleavings; actual radio/USB commissioning remains required.
2. Badges activate online only. Current 8-hex badges are matched at the current site before any numeric order interpretation. A lookup failure must never fall through to order handling. For offline input that is ambiguous between an eight-digit badge and an order, reject loudly and clear that scanner identity rather than guessing; unambiguous six-digit slips or explicitly # prefixed full orders can queue for the bound person. Do not silently turn an offline badge attempt into work credited to the old person. Known badge collisions take badge precedence; unknown nonnumeric tokens reject. Existing numeric packing-slip normalization may be reused, but pin exact supported shapes (full numeric order or legacy six-digit code) and reject everything else. A pending badge clears the old person immediately; an order arriving before activation is loudly rejected. Ten minutes of framing inactivity expires that scanner's identity. Reload, auth/site/mode changes clear identities. Each accepted order captures its person synchronously before any await.
3. Badge activation RPC validates caller owner/manager/kiosk and site, active badge and existing person with site membership. It returns only person ID/display name. Under a worker/site lock it automatically creates a stable-id clock_in only when necessary for the current site workday, using server UTC time and existing site zones/04:00 boundary. Repeating or switching scanners must not double-clock in. Same-request lost-response replay is safe; role checks precede replay. Clock-out remains in the existing flow; scan-only makes no estimated timing claims.
4. Durable queue persists request UUID, backend/caller/site/receiver scope, scanner, person, badge, original UTC scan time and normalized order before network work. IndexedDB storage failure is a rejection, never in-memory acceptance. A raw queued order is resolved when online, then its exact validated lines/component quantities/packaging payload are persisted before commit. Retries of an uncertain commit reuse the exact payload and IDs. Processing is serialized; IndexedDB transactions prevent job loss across tabs, server receipts prevent duplicate posting. Jobs survive reload, but never drain under another caller/site. Bound queue size and show storage/corruption errors without silently dropping rows. Retain blocked jobs with reason and retry/fallback instructions.
5. Automatic selection uses strict existing SKU routing, not fail-open isLineMyDept. Save A0 and regular framed lines, aggregated by SKU, with raw quantity; use existing multiplier for item display. Unframed/gift/accessories receive no framing credit. Reject canvas, unknown/legacy/blank SKU, invalid quantities, no framing lines, cancelled orders, edit-warning tags and open replacement/CS cases to classic. Add hasNextPage/truncated to Shopify lookup; strict mode refuses an incomplete response. Do not add pagination or infer work-site from shipping country. Enforce caller/worker/queued site; Shopify's shared store has no authoritative work-site field.
6. One server RPC atomically saves a framing scan: authenticate; compute canonical payload hash itself; take per-site/order advisory lock; replay matching receipt or reject changed payload; check existing noncancelled verification/completion; insert one deterministic line_verified per SKU and one completed per touched work type; perform the appropriate component deductions and A0 F4 packaging; write receipt. Existing/partial prior work is an explicit already-recorded/manual-fallback result, never extra credit. Do not rewrite old events. F5 triggers receive original occurred time and bound staff_id. Unknown outcome cannot be edited into a new request until resolved.
7. A0 terminal completion requires F4 automatic mode, a usable rule set and a fully resolved prediction. Compute with existing F4 helpers and persist the rule version/target/snapshot with the job. Server validates scope and payload and calls packaging_apply inside the transaction. Missing stock codes or unposted packaging reject atomically with clear fallback. Existing negative-stock behavior may remain, but return/display its warning. Ordinary framed work still deducts at dispatch. Do not silently skip packaging or invent rules. Classic scan-box mode remains available; disabling shared mode never deletes its pending queue.
8. Fix the legacy deduction race in an append-only migration, preserving its signature and routing behavior: authorize caller/event/site, acquire the same per-order lock, re-read state/check ledger under lock and process products in stable order. All existing callers then share serialization. No duplicate stock engine or unique index requiring historical cleanup. Keep old idempotency keys compatible; resolve product code/id aliases without creating a second charge. Tests must include classic/new concurrent calls and request retries.
9. Wall UI shows S1/S2/S3 identity/expiry, large last saved/queued/rejected result with person/order/pieces, queue count and recovery. Distinct error sound, focus/visibility/offline/auth warnings. One operator start gesture may enable browser audio and wake lock; badge/order scans have no confirm pop-ups. Reacquire wake lock after visibility changes, feature-detect unsupported devices. Document browser/OS kiosk auto-start and retained kiosk login; web code cannot configure OS startup.
10. Minimal health: current receiver heartbeat every minute, last accepted scan time and queue count; a manager/owner status card shows stale heartbeat after 3 minutes and no scans after 30 minutes during configured site-local work hours (default weekday 08:00-18:00). No email, cron or telemetry history. Bound table to one current row per caller/site/receiver; no worker/rate data. Closing the receiver page can thus show stale elsewhere. Local warnings do not claim remote notification.

## Hardening and acceptance

Network/Shopify/Supabase outage: durable queued or visible rejected, never green. Changed account/site, revoked badge and removed person cannot rebind an old scan. Server validates bounded inputs and uses pinned search paths/revoked default function grants; new tables have RLS and no direct receipt writes. Owner/manager/kiosk may operate within their site; staff/CS/anon cannot gain shared-station authority. Queries are indexed by site/order/request or current receiver, not months of events. No new secrets, provider writes, purchases or dependencies.

Meaningful checks: strict parser, simultaneous bursts and stale badge race; queue reload/storage failure/account switch/lost response; mixed A0/regular/unframed/set quantities; all-or-nothing failure; exact-once credit and stock for duplicate/concurrent/classic calls; revoked/cross-site roles; F4 auto prerequisites and regression. Run focused checks per task, one complete typecheck/test/build gate and a fresh branch review. Execute reviewed SQL on isolated staging, plus browser happy/error/queued flows. Physical scanner range/interleaving, real rule commissioning and future F1/F8 timing/report work remain explicitly separate.

Release: expand-only migrations 0055 onward (0048-0051 are reserved for F3; 0052-0054 F5). Apply reviewed staging schema, deploy combined Preview with staging env, opt in on a test receiver. Rollback to classic/previous Preview; keep queue/receipts/history. Never production or main in this task.
