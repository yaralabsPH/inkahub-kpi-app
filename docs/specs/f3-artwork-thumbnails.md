## Problem

People at production stations need to recognise the actual artwork on an order. F2's `OrderLineDisplay` currently reserves a 64 × 64 image space. The separate `ProductImage` component retrieves full artwork through expiring Dropbox links, caches by full SKU, and can keep a missing result or expired URL for the rest of the tab session. It is not currently wired into `OrderLineDisplay`.

The server does not generate or permanently store thumbnails. Its set lookup selects component 01, and its keys disagree with the client. A new product can arrive before its source file. Refreshing the browser must not be the recovery mechanism, and image failures must never block verification, completion, dispatch or clock events.

This draft specifies the whole F3 pipeline. Roadmap approval and the recorded amendments establish the requirements; this document itself still needs CJ's review. Recommendations marked as open below are not settled product choices.

## Goals

- One permanent, small thumbnail per canonical `artworkCodeFromSku` result, shared across all sizes and frame variants and all sites using this artwork library.
- Show actual artwork with the line's frame-colour border, retaining F2's large colour block, size, title, quantity and actions.
- Queue immediately on Shopify product/variant changes, Dropbox source changes and an order missing a thumbnail. Recover missed work through scheduled reconciliation.
- Meet the recorded two-minute target under normal service: from accepted trigger, with all required sources available, to a published thumbnail visible in the open order. Missing sources, provider outages and exceptional backlog are visible exceptions, not silently successful work.
- Refresh replaced artwork safely, survive duplicate/out-of-order events and worker crashes, and give owners/managers a useful failure list.
- Complete one resumable catalogue backfill at launch. Routine new/changed artwork must thereafter work automatically.

## Non-goals

- Packing-slip layouts, rendering, printing, exclusions, PDFs, Make scenarios or their tracking sheets. Make Part 6, `/Packing Slip Previews/` and its index remain read-only throughout F3, including backfill and recovery.
- Shopify product photos, frame-specific generated images, changing source artwork, or writing SKUs/products back to Shopify.
- Changes to production routing, work attribution, inventory deductions, item counts or report history. An image is never evidence that an item was printed, verified or completed.
- A manual generator or recurring manual backfill as the normal operating model.
- A Dexie clone of the Supabase production workflow; a broader order-lookup or legacy-SKU redesign.

## User stories / flows

1. **Station/order view:** an authorised user opens an order. The page collects unique artwork codes, requests their status in one batch, and renders the existing order controls immediately. Ready art appears without a Dropbox or Shopify call from each row. Missing art is durably queued and shows “Preparing artwork”. The page refreshes pending status until ready or failed.
2. **Variants:** the same art in A1 black and A4 natural uses the same object. The UI draws different black/natural borders. White and black have an outer contrasting ring in both themes. Unframed/canvas use a neutral outline and their existing style text, never an invented frame colour. Artwork uses `object-contain`, preserves orientation/aspect ratio, and has accessible text.
3. **Sets:** resolve all numbered components in order. Recommended presentation is one composite, left to right then top to bottom, with equal cells, no cropping and a neutral background, plus accessible “Set of N” text. Never show component 01 as if it were the whole set. Missing/ambiguous components leave the whole thumbnail pending or failed; no partial composite is labelled ready. Composite versus another complete-set presentation remains a CJ choice.
4. **Non-artwork:** gift card, frame-only and AUX-other show explicit “Gift card — no artwork”, “Frame only — no artwork” and “Accessory — no artwork” placeholders. They do not enqueue jobs. Free prints do have art even though KPI counting excludes them. Unknown/malformed/blank SKUs show “Artwork unavailable — SKU not recognised”, never a guessed image or a false “no artwork required”.
5. **New/changed product:** a verified Shopify event persists work immediately. If the source has not arrived, the order shows “Waiting for artwork file”; the queue survives with no `artwork_images` row. Dropbox arrival wakes it automatically. Product title/price-only changes with the same art revision cause no conversion.
6. **Replacement:** when any source component changes, hide the previous image on active order rows once the new desired revision is known and show “Updating artwork”. Keep the previous object for rollback/audit. Only the complete current revision becomes ready. A slow old worker cannot restore the previous image.
7. **Failure:** recommended shop-floor text is “Artwork unavailable — tell a manager”, with a warning icon and artwork code; verification remains usable. Offline/status-fetch failure is separately “Artwork status unavailable”, not a claim that generation failed. Final wording/action is open; visible failure itself is binding.
8. **Administration:** add an **Artwork thumbnails** panel to Settings for owners/managers who have Settings navigation access. Show pending/failed counts, oldest pending age, last Shopify/Dropbox receipt, last cursor/reconciliation success, and a paginated failure list (code, safe reason, attempts, first/last failure, next retry, revision, source component). Provide bounded “Retry selected”, backfill progress/resume and health checks. No secrets, customer details or signed URLs in diagnostics. Role checks also run on the server; staff/kiosk/CS cannot administer jobs by calling the endpoint directly.
9. **Emergency switch:** the owner can turn off thumbnail display without deployment. Orders retain their reserved placeholder and all F2 information/actions. A separate owner control pauses generation while verified webhook intake remains durable. Re-enabling resumes saved work. Managers can inspect/retry failures but do not control the global switches.

## Data and backend impact

### Canonical identity and exact source selection

`artworkCodeFromSku` in `src/lib/domain/skuRouting.ts` is the authority. Share its pure parsing/key contract with `api/` through a server-compatible import/module; do not maintain a second approximate regex parser. Preserve existing routing/counting behaviour.

| Example SKU | Canonical key | Expected ordered source identities | Old server cache key |
| --- | --- | --- | --- |
| `INKA-KAN0566-A4-FB` | `KAN0566` | `INKA-KAN0566` | `KAN0566` |
| `INKA-S3WIL0049-A2-FN` | `S3WIL0049` | `INKA-S3-WIL0049-01`, `-02`, `-03` | `S3-WIL0049-01` |
| `INKA-AUX-FP-ESP-A2` | `ESP` | `INKA-AUX-FP-ESP` | `AUX-FP-ESP` |
| Gift/frame-only/AUX-other | none | none | none |

Use `dropboxFilenamesForSku` to establish expected component count/order, then reconcile actual file names through explicit, tested aliases. The current index includes free-print names such as `INKA-AUXESP`, `INKA-AUXMCO` and `INKA-AUX-FP-MCO-A2`; these are candidates for `ESP`/`MCO`, not new canonical keys. Do not map unrelated printed inserts such as AUXIMH into a free print by substring. Confirm each alias against the intended artwork before enabling it. If size-labelled sources for the same canonical code contain different artwork, raise a conflict instead of creating size-specific thumbnails.

Initial source discovery recursively indexes the configured master folder (reference: `/INKA Hub`) through Dropbox pagination. Store exact file ID, normalised path, original filename, byte size, `content_hash`, `rev`, deletion flag and observation generation. Permit supported image extensions and verified extensionless files. `_FIXED`, repeated extensions and separator variations in the reference are not permission for arbitrary fuzzy matching: enumerate/test accepted patterns, and treat multiple distinct current candidates as ambiguous. Never use “first search result”, “prefer any JPEG”, or lexicographic hash/rev ordering to decide freshness. No arbitrary client-supplied source URL/path is accepted.

Maintain an explicit canonical-to-component mapping with ordinal and exact file ID. The resolver uses current Dropbox metadata; an index's single hash alone is not current-source proof. Multiple paths with identical content can share component bytes, but selection of the authoritative source path must remain deterministic and recorded. A missing, moved, deleted or conflicting source invalidates readiness and is reconciled; it does not authorise choosing another visually similar file.

Reconcile old set/free-print keys by adding canonical mappings/rows after verification. Keep old alias rows intact for old code; do not rename primary keys, delete legacy data or copy component-01 URLs into a complete-set pointer. `dropbox_path` remains NOT NULL. Only create the canonical `artwork_images` row once there is a verified real source path (for a set, component 01's real path is a legacy compatibility field; the full manifest is authoritative). Unresolved artwork lives in the new state/queue tables.

RLS is enabled on every new exposed table. Explicit grants/revokes accompany policies; migration 0003 grants future public tables/functions broadly, so “no GRANT in this migration” is not security. Server-only source/inbox/queue tables get no `anon`/`authenticated` access. Expose a safe status projection through the authenticated API; any direct view must use invoker security and appropriate base-table policies. No secrets are stored in readable settings/status.

Workers claim due rows atomically using row locks/`SKIP LOCKED`, a lease and an incrementing fencing token. Claims, counters and status transitions are transactional. Recommended lease is 120 seconds for a worker capped at 90 seconds; reclaim only after expiry. A resumed worker must still hold the current token at every checkpoint/publication. Successful continuation claims do not consume the failure budget. An uncheckpointed crash/expired lease consumes one failed execution exactly once before reclaim; lease expiry cannot create infinite free retries.

Job states are `queued`, `waiting_source`, `running`, `retry_wait`, `succeeded`, `failed`, and `superseded`. Recommended maximum is six failed executions per revision/resolution generation (initial failure plus five retries), with jittered delays of 30 seconds, 2 minutes, 10 minutes, 1 hour and 6 hours. A resolved N-component job has at most N component steps, one composition step and one publication step; bound its claims to N + 8 including failures. Source-resolution work has its own six-failure budget. An intentional provider cooldown before execution does not spend an attempt or claim an image lease. Honour longer `Retry-After` delays and shared provider cooldowns. Validation/ambiguity/unsupported-format errors can fail immediately; 429, timeouts and 5xx retry. Missing source waits within this budget, then fails visibly. A later verified source arrival/change creates a new generation automatically; ordinary row renders and unchanged reconciliation do not reset a terminal failure. Owner/manager retry is an audited, idempotent reset of selected failed work, not a new duplicate job. Credential repair may resume the bounded affected queue in an owner action.

Each completed component is uploaded to a separate **private internal work bucket**, keyed by manifest/ordinal/content/output digest. Persist its path, dimensions, bytes and checksum in the job checkpoint before releasing the lease. Later invocations validate and reuse these small objects; `/tmp` is never a durable checkpoint. Compose from all checkpointed components, then publish the final object. Work-bucket reads/writes are service-only even if CJ chooses a public final-image bucket. Bound cleanup to completed/superseded job intermediates after seven days; retain intermediates for pending/failed work and never delete final published or rollback objects through this cleanup.

### Revision identity, publication and invalidation

- `rev` identifies the exact Dropbox file revision; `content_hash` identifies bytes. Neither is a sortable freshness clock. Store both plus file ID. For a set, compute a deterministic manifest digest over **all ordered** `(ordinal, file_id, rev, content_hash)` entries and a renderer version. Singles/free prints use the same one-component manifest structure.
- Mark source state dirty when a verified trigger arrives. Serialize resolution for each artwork and fence it with a database generation/token. Do not let an older scan snapshot replace a newer observation; initial/full scans stage results under a scan epoch and reconcile intervening cursor changes before declaring them current. Shopify events trigger current reads rather than installing an old event payload as current truth.
- Render exact pinned revisions, verifying returned metadata and, for original downloads, Dropbox's content hash. If the endpoint cannot pin that revision, compare metadata before/after fetching and discard mismatches. A replacement during download is retried as new work.
- Immutable objects use a path such as `v1/<canonical_code>/<manifest_digest>/<output_sha256>.jpg`. The last digest checks output bytes; a Part 6 filename is a **source** hash, not the JPEG's own SHA-256. Upload without overwrite. An existing object is reused only after its expected metadata/checksum is verified.
- After upload, revalidate current source metadata and perform one transaction that compares desired generation, manifest and active lease, checks that generation remains enabled, updates the nullable `artwork_images` pointer, and marks state/job ready/succeeded. A newer dirty generation or different revision makes the old job superseded, with no pointer/status change. An administrative pause retains the completed checkpoint for resumption and is not a generation failure. An upload without publication is an orphan, not success.
- Keep the old object and pointer history; a new path invalidates browser/CDN caches naturally. No in-place replacement at a stable object path. Active rows follow current art, not a historical order snapshot; no production history is rewritten.
- Client cache keys include backend/project, session identity, canonical code and published revision. Batch status checks invalidate on changed revision. Retire the `dropbox_img:<full sku>` / `__missing__` convention; pending/failure is not permanent session cache. Signed URLs carry expiry and refresh in a batch before expiry; an image load error gets one metadata/URL refresh, then visible failure. Clear private caches at sign-out/account/environment change.

### Image source and generation decision

The proposed production generator is **Sharp in a bounded Node Vercel worker**, independently of Part 6. Add and lock the `sharp` dependency for real resizing, validation, orientation/colour conversion and set composition. Never bundle it into Vite. The implementation plan must verify the deployed Node ABI/native package and bundle size.

Compare the available sources:

| Approach | Decision and reason |
| --- | --- |
| Verified Part 6 JPEG | Recommended optional launch seed. Read current original metadata, resolve each exact component, require a matching current `content_hash` in a valid v1 index entry, then read and decode the corresponding JPEG (≤400 × 400, ≤75 KB). Reject missing/ambiguous/stale data. Copy resulting art only into F3 Storage. Cannot be the automatic future source because the reference generator is manual. |
| Dropbox `get_thumbnail_v2` | Optional fast path for eligible sources up to its documented 20 MB limit, with revision validation and no cropping; still normalise/validate with Sharp. Not sufficient for 150 MB originals, extensionless sources or set composition. The official SDK reference lists supported extensions and the 20 MB restriction; it does not establish safe conversion of every 300 MP input. [Dropbox thumbnail API](https://dropbox-sdk-python.readthedocs.io/en/latest/api/dropbox.html#dropbox.dropbox_client.Dropbox.files_get_thumbnail_v2). |
| Original download + Sharp | Required automatic fallback for new/replaced artwork without a verified small preview. Fetch directly from Dropbox to bounded temporary storage, verify the revision/hash, reduce one component at a time, then compose only reduced images. No original passes through a browser or incoming HTTP body. |

Proposed F3 envelope: originals ≤150,000,000 bytes and ≤300,000,000 pixels; supported decoded JPEG/PNG/WebP/single-page TIFF including valid extensionless sources. Reject animation, multipage files, malformed content and formats not tested. Inspect dimensions, channels and bit depth before conversion. Do not set `limitInputPixels:false`, `unlimited:true`, or import the reference's 500 MP JPEG exception. Sharp's default pixel ceiling is about 268 MP, so the explicit bounded 300 MP setting is necessary. [Sharp constructor](https://sharp.pixelplumbing.com/api-constructor/).

Use orientation correction, sRGB conversion, white transparency flattening, `fit:inside`, no enlargement and JPEG output ≤400 pixels per side / 75,000 bytes. Try a bounded quality sequence (78, 65, 50); fail if still oversized. For composites reduce each component first and arrange all cells in a maximum 400 × 400 canvas. Do not crop art to fit. Limit Sharp native concurrency to one and disable or tightly cap its operation cache; `fastShrinkOnLoad` helps JPEG/WebP but is not a universal memory bound. [Sharp global properties](https://sharp.pixelplumbing.com/api-utility/), [resize options](https://sharp.pixelplumbing.com/api-resize/).

**Resource gate, not an untested performance promise:** 300 MP × 4 one-byte channels is already 1.2 GB before decoder, colour-transform and Node overhead; higher bit depth uses more. Propose a verified 4 GB Vercel worker allocation, one global large-source conversion at a time and no concurrent original buffers. Stream/hash to temporary disk, cap scratch use at 200 MB per active original, clean it in `finally`, and checkpoint each reduced component. Use a killable conversion subprocess with a 45-second conversion deadline; cap the whole invocation at 90 seconds (configure 120-second function duration). Downloads have a 30-second deadline and a streamed byte cap even if headers lie. A timed-out child is terminated, not left decoding after a rejected promise. Native cache limits do not cap total RSS.

Vercel documents 2 GB default memory and up to 4 GB on Pro/Enterprise; duration limits depend on plan and Fluid Compute. These are platform maxima, not this project's settings. [Function limits](https://vercel.com/docs/functions/limitations), [memory configuration](https://vercel.com/docs/functions/configuring-functions/memory), [duration configuration](https://vercel.com/docs/functions/configuring-functions/duration).

The approved implementation plan must make the bounded converter and its staging benchmark an early feasibility task, before building the remaining integration around an unproven worker. CJ deploys that test build to Preview. Prove the Node/native/subprocess packaging and the largest supported JPEG, PNG, TIFF, extensionless, high-bit-depth and set cases: peak combined RSS <3 GB, scratch <200 MB, no termination, and normal-service end-to-end timing. Include incompressible and corrupt fixtures, not just easy solid colours. This is a gate within authorised implementation and before release, not permission to build a pre-plan spike now. Actual source-format distribution, worst-case decode memory, bandwidth, configured Vercel plan and these timing measurements were **not verified** in this docs-only task. If the envelope fails, stop dependent implementation and record a proposed dedicated bounded conversion service and cost assessment in the plan's open questions for CJ; do not silently reduce coverage, substitute Shopify photos or require manual future generation. Over-limit art fails visibly and is listed for correction.

### Triggers, worker dispatch and reconciliation

1. **Shopify:** add `read_products` to the existing install scope list and reauthorise the environment's app/token. Register `products/create` and `products/update` at a pinned supported API version. Shopify documents that updates include variant additions/removals/updates; product payloads only fully describe the first 100 variants, so persist product ID and page current product variants in the worker. Do not assume a separate `variants/create` topic exists or that the webhook payload is complete. Fetch SKU/ID/update fields only, not product photos or customers. A test with >100 variants must pass. [Webhook topics](https://shopify.dev/docs/api/webhooks/latest).
2. Verify `X-Shopify-Hmac-SHA256` over the **raw body** using `SHOPIFY_CLIENT_SECRET` (not Admin token), constant-time comparison, allowed shop/topic and bounded input before processing. Deduplicate by configured shop plus event/delivery identity and coalesce by canonical art/revision. Persist the inbox record before 2xx, returning a retriable error if durable acceptance fails. The OAuth callback's query-string HMAC routine is not a webhook verifier. [Shopify verification](https://shopify.dev/docs/apps/build/webhooks/verify-deliveries).
3. **Dropbox:** GET verification echoes a bounded challenge as plain text with `nosniff`. POST verifies `X-Dropbox-Signature` (HMAC-SHA256 of raw body using the app secret), validates the configured account, then durably marks it dirty. Notifications identify accounts, not filenames. Bootstrap recursive `list_folder`, persist its cursor, and drain `list_folder/continue` until `has_more=false`, committing processed changes/jobs and the new cursor together per page. One lease owns an account/folder cursor. Handle deletes/moves and component changes; never advance the cursor before durable processing. Cursor reset/expiry starts a resumable full reconciliation, not an empty-success reset. Repeated notifications during a drain leave a dirty marker for another pass. [Dropbox webhooks](https://docs.dropboxapi.com/dropbox-api/docs/webhooks), [list-folder contract](https://dropbox-sdk-python.readthedocs.io/en/latest/api/dropbox.html#dropbox.dropbox_client.Dropbox.files_list_folder).
4. **On demand:** a batch request for the currently displayed SKUs returns status and idempotently queues genuine missing artwork. Validate JWT/profile, permitted order-related navigation and active site membership; limit to 100 SKUs / 16 KB per request. Resolve known catalogue/mapped codes locally. A previously unseen valid code can enqueue only a bounded discovery request, not arbitrary remote downloads. No client may set source path, revision, desired generation or storage URL. The UI never waits for conversion.
5. **Immediate dispatch:** after committing new work, kick the internal worker through a supported post-response lifetime primitive (proposed `waitUntil` from `@vercel/functions`). This additional small dependency must be justified in the plan; an unawaited promise is not durable execution. The database queue is authoritative if the kick fails. Authenticated internal calls use a separate worker secret and a configured origin, never a request Host header. Persist only IDs, not credentials. [Vercel functions API](https://vercel.com/docs/functions/functions-api-reference/vercel-functions-package).
6. **Scheduled safety:** recommend a one-minute worker/cursor recovery tick, a 15-minute bounded incremental catalogue reconciliation and a daily paginated full catalogue/source audit. Each uses persisted checkpoints, bounded pages and overlap-safe leases. Incremental product watermarks overlap and deduplicate; a full audit catches missed deletions/older changes. Stuck leases and genuinely missing/current-revision work are repaired automatically. Unchanged terminal failures are reported, not retried endlessly. Existing digest schedules remain intact.
7. Cron handlers require `Authorization: Bearer <CRON_SECRET>` on every path. A browser session or cron-looking header does not authorise them. Vercel's documented legacy cron minimum is daily on Hobby versus per-minute on Pro/Enterprise; a Hobby daily tick cannot provide reliable two-minute recovery. CJ must confirm plan/cadence. Preview scheduling must be tested with a protected staging-only runner/manual tick because a production cron registration does not prove Preview execution. [Cron limits](https://vercel.com/docs/schedules/cron-jobs/usage-and-pricing).
8. **Launch backfill:** start one owner-authorised run with a stable idempotency key. Page the whole Shopify catalogue and every product's variants, union with discovered artwork/source mappings and verified legacy-cache candidates, canonicalise/deduplicate, then enqueue through the same pipeline. Resume by saved cursor/checkpoint after interruption; never rescan all completed work on each invocation. Live on-demand/replacement work takes priority. Coverage shows discovered/ready/pending/failed/unsupported counts and unresolved code lists. CJ reviews all exceptions before enabling the display; no requirement for later manual bulk backfills.

### Roles, Storage and the legacy RPC hazard

Recommended bucket is **private**, with expiring signed URLs minted in batches after authorisation. Store object paths permanently, not signed URLs as identity. A proposed 60-minute URL lifetime with refresh five minutes early keeps an open tablet working. Public versus private remains open: a public bucket makes artwork readable by anyone with the URL, regardless of table RLS. [Supabase bucket access](https://supabase.com/docs/guides/storage/buckets/fundamentals).

| Role | Artwork/status read | On-demand enqueue | Failure list / retry | Global controls / launch run | Direct F3 writes |
| --- | --- | --- | --- | --- | --- |
| owner | Yes | Yes | Yes | Yes | No; authenticated API only |
| manager | Yes | Yes, authorised site/screen | Yes, Settings access | No | No |
| staff | Yes | Only with relevant granted screen and site | No | No | No |
| kiosk | Yes | Order submission at assigned site | No | No | No |
| cs | Yes | Authorised CS/order view at assigned site | No | No | No |
| anon / missing profile | No | No | No | No | No |
| service role in `api/` | Internal | Internal | Internal | Validated actions | Queue, metadata and Storage writes |

Artwork is a shared non-customer library, as in 0024, so its safe read/status is global across these roles; this does not expose orders, customers or financial/site data. Existing navigation grants are retained. F3 first integrates the existing station/order line component, not procurement `/orders` or a new customer-order screen. Reusable image components used elsewhere follow the same access rules.

For the private final-image bucket, Storage SELECT policies restrict access to this bucket and a valid profile role; no anonymous SELECT. No authenticated INSERT/UPDATE/DELETE policies may admit its objects; no upload/upsert rights for managers or kiosks. Only the service worker uploads new immutable paths. The separate work bucket has no anon/authenticated read or write policies. An API signer must derive final-image paths from protected published state, never sign arbitrary caller-supplied paths or work objects. Check existing permissive Storage policies in staging because policies combine. If CJ chooses public final-image access, document public image reads explicitly while keeping all write restrictions and the private work bucket.

**0024's definer RPCs are callable directly by authenticated users.** Their API's JWT check does not protect direct RPC invocation. New enqueue/claim/publish RPCs must explicitly revoke EXECUTE from PUBLIC, anon and authenticated (including inherited/default grants), grant only the intended service role, pin `search_path`, validate inputs and enforce revision/lease transitions. Prefer invoker functions where possible.

Do not extend the old upsert RPC to accept `storage_path` or jobs. The old RPCs may still change legacy `dropbox_path`/`cached_url`; F3 treats those as untrusted discovery hints and never uses them to sign a Storage path or publish readiness. Add a narrowly scoped guard for F3-managed rows: non-service callers cannot change the new columns, change their key, or delete a row with an F3 publication, including through the old definer delete RPC. Authorise the guard using the verified request role, not `current_user` (which a definer changes). Allow old legacy URL-field refreshes so rollback readers still function; the separate protected manifest remains authoritative. Verify old code's stale-path branch still returns an image even when its best-effort deletion is refused. Existing unmigrated legacy-cache vulnerability is recorded, not copied into new trusted writes; broader legacy RPC retirement belongs to a later compatible release.

## Hardening

### 1. Failure modes

Order controls render independently of image status; no network or image job blocks a scan/save. Failed durable enqueue returns a truthful unavailable status, not “queued”. Provider failures preserve work and last safe checkpoint. Database leases, unique keys and fenced publication handle two devices/workers. Invalid/unknown SKU is visible and does not cause fuzzy search. Existing cancellation and site checks remain authoritative; thumbnail status neither enables a cancelled order nor infers a site. Make/Slack failures are n/a to this pipeline because F3 does not call them.

### 2. Data correctness

Canonical keys and ordered manifests are shared rules. Replacements update current display art only; production events, quantities, attribution and history remain unchanged. F3 set image composition is not a second item-count rule. All timestamps use UTC `timestamptz`; administration displays the selected site's zone (AU Sydney, UK London, US Chicago), with labels. Source observation, generation and completion times remain separate; a seeded preview records provenance and validation time, not an invented source-creation time.

### 3. Security

JWT/profile/site checks protect user actions; HMAC protects webhooks; secrets protect internal/scheduled calls. Raw bodies are bounded before parsing, signatures checked before work, errors sanitised. Only configured Dropbox/Shopify hosts and roots are fetched. Reject user URLs, redirects to arbitrary hosts, traversal, unknown buckets and source-path overrides. All five roles, grants/default privileges, definer functions and Storage policies are tested directly. Shared art has no customer payload. Secret values never enter source, response diagnostics or logs.

### 4. Release and rollback

Release is one **bulk batch run by CJ**, not separate agent deployments of F3 slices. Proposed ordered runbook:

1. Before implementation, CJ reviews the open choices and approves the eventual spec/plan. During implementation, complete the early worker feasibility gate on Preview. Before the release window, close the evidence/resource gates and check combined branch review and CI. Reconcile F1's 0034–0046 and F3's next available ≥0047 numbers. Apply/test expansions on staging, then complete the Preview tests and old-version compatibility test.
2. Choose a quiet window away from shifts/digest times. Record the exact current production deployment as rollback target and verify its legacy Dropbox credential works. Record existing provider subscriptions/configuration; back up production schema/data and confirm Storage recovery arrangements.
3. CJ sets Production server variables and scopes, separately from Preview, **before merging**. Reauthorise Shopify with existing scopes plus `read_products`; obtain Dropbox refresh credentials/read scopes. Confirm worker memory/duration/cadence. Provision final-image and private work buckets and apply the batch's additive migrations in dependency order. Display and generation controls remain off; old code must still work.
4. CJ merges the reviewed bulk release; Vercel deploys once. Check environment identity, worker secret/cron guards and Sharp native availability. Register F3 Shopify/Dropbox webhook URLs only once the handlers exist; finish Dropbox challenge and initialise saved folder cursor with a full inventory. Verify registrations and durable receipts. A post-registration reconciliation catches changes during setup. Do not modify Make or its preview index.
5. CJ enables generation with display still off, starts the single resumable launch backfill and watches priority work, failures and resource budgets. Validate optional seeds against current sources; review every unresolved launch artwork. Reconcile current catalogue/source changes after backfill. Record coverage and no outstanding unexplained mappings.
6. CJ enables display, verifies a small operational sample and normal-service timing, tags the bulk release, and watches logs/health for at least 30 minutes. Confirm actual scheduled execution, cursor advancement and subsequent product/file automatic processing. Existing daily digest delivery is checked on its normal schedule.

Rollback order: (1) owner switches display off immediately, then pauses generation if faulty/costly; (2) CJ disables only F3 provider subscriptions/scheduler targets if intake is the problem, retaining queue/cursors and recording the gap; (3) CJ uses Vercel Instant Rollback to the recorded compatible deployment and performs the release smoke checks; (4) CJ fixes forward/reverts the bulk merge through a reviewed branch as appropriate. Do not undo expansions, delete jobs/Storage objects, restore a database backup over new work, edit old migrations, remove `CRON_SECRET` or disturb the digest/Make flows. If old code lacks F3 handlers, paused subscriptions avoid futile deliveries; reconciliation catches the gap when restored. Keep `cached_url` columns, legacy aliases and the old authenticated image route throughout the rollback window. A feature-off UI uses safe placeholders, not an automatic return to per-row original downloads.

### 5. Performance and bounded cost

- Batch status/signing at most 100 unique codes per request; one cache shared across rows/variants. Poll only visible pending work every 5 seconds initially, backing off to 15 seconds after two minutes; background/hidden tabs stop polling. Ready metadata and controls revalidate at most every 60 seconds or on focus. Storage image delivery is expected; Dropbox/Shopify calls per row are prohibited.
- Keep read-only batch status polling separate from the cost-bearing resolve/enqueue endpoint: initial allowance 120 status reads per authenticated account per minute, supporting multiple tablets sharing a kiosk account, plus 12 resolve/enqueue requests per account per minute. Test at least three such tablets polling and loading new orders concurrently. Discovery adds limits of 30 new codes per user per hour and 300 globally per hour; admin actions allow 10/minute and at most 50 codes per retry action. Enforce in durable/shared state, not per-process memory. Status reads never enqueue or call providers. A large valid view is paginated/cached; throttling returns a retry delay and never disrupts order controls.
- One global large conversion, up to two small-preview/composition tasks; worker invocation processes at most one original or ten small components, with the 90-second cap and checkpoints. Fair scheduling prioritises on-demand/replacement work and reserves backfill progress without starving it. A worker can hand off continuation after checkpoint, bounded by the same shared quota.
- Start with provider budgets of 60 Dropbox requests/minute and 20 Shopify GraphQL requests/minute per configured account/shop, further limited by actual provider cost/throttle responses. Each scanner/reconcile invocation reads at most one page (proposed 100 products/files/variants); save cursors and continue later, never silently truncate. Deduplicate source/content work before downloads. Apply daily byte/conversion budgets (proposed 10 GB original downloads and 1,000 conversions for routine work; an additional launch allowance capped at 50 GB and 5,000 conversions/day), with visible budget-paused health and owner adjustment. Both share the same provider/concurrency limits. Budget pauses are degraded service, not satisfaction of the latency target.
- Index due jobs, code/revision, source file/path, inbox identity and sync cursors. Never query months of production events to display art. Page failure/history views with stable keys. Estimate Storage/egress from unique artwork/revisions, not order quantity; monitor old-object/orphan growth. Current referenced objects have no automatic expiry. Any later cleanup retains active/rollback references and uses a separately reviewed retention policy.

### 6. Operations

Settings reports counts and oldest queue age, terminal failures, rate/budget pause, webhook receipt age, cursor lag, last complete reconciliation, backfill progress and ready latency. Log job/event IDs, canonical code, safe error class, attempt, elapsed time and bytes; omit tokens, signed URLs, customer/order payloads and raw provider errors. Owner/manager checks the panel during launch and after provider changes; overdue work (>120 seconds with source available) is visibly degraded. Manual shop-floor fallback is existing title/SKU/size/colour/quantity and normal verification, never an instruction to assume a missing image is correct. Maintain subscriptions/scopes, refresh-token revocation handling, configured API version, native dependency updates, spend/egress and Storage growth. No new Slack/email messaging is required.

### 7. Tests

Unit tests cover canonical single/set/free-print/unknown keys, exact aliases and near misses, component order/completeness, manifest hashing, image limits and queue transitions. API tests cover JWT/role/site/method/body guards, raw-body HMAC, idempotency, retry limits, rate limits, cursor commits, expiry and no external calls from cache hits. Database integration tests exercise real concurrent claims/publications, explicit grants, definer attacks and all Storage role denials in staging. Frontend tests cover pending/failed/offline/non-artwork/disabled states, colour borders, stale URLs, account changes and Dexie's no-network path. Native/Preview tests validate actual conversion resources. Run `npx tsc -b`, `npm run test -- --run`, `npm run build`, and a dedicated F3 API type-check/test command in CI: the normal TypeScript project excludes `api/`. Inventory/money behaviour changes are n/a; preserve existing tests and the exactly-once stock smoke check to prove isolation.
