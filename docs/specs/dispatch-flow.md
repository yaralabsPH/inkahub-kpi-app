# F7: Dispatch flow

Approved for autonomous implementation under CJ's delegation. Base: reviewed F6 0c47ace4527090510d0743157b37d9181192f8ce. Migration 0055 is installed on staging and immutable; use 0056 onward. Staging only, existing isolated branch chain, no production or main.

## User result

The dispatcher scans their badge once for the shift, then scans order slips. The order view shows who framed each framed SKU. A missing framing record gets a short warning and a name picker. Saving that choice records manual attribution clearly, without inventing a framing scan or timing. Keep this within the existing Production/receiver UI, with a small Reports addition.

## Decisions

1. Reuse F6's strict scanner framing, per-scanner identity, durable outbox, original scan time, caller/site scoping and atomic receipt infrastructure. Add dispatch as an explicit receiver mode. Changing mode clears identities but retains pending jobs with their original mode. Normal framed evidence plus valid packaging saves automatically; exceptions remain visible and queued/blocked. Do not alter the classic framing/dispatch handlers beyond adding a reusable evidence display where practical.
2. Dispatch badge identity lasts until the next site-local 04:00 workday boundary or twelve elapsed hours, whichever comes first. Reload, sign-out, site/mode change and an explicit switch-worker action clear it. There is no one-minute idle timeout in this new dispatch mode. Online activation and revoked/cross-site validation follow F6; offline ambiguous eight-digit input never reuses an old person's identity. Do not modify classic-mode session rules incidentally.
3. Resolve framing evidence by exact site, normalized order and aggregated framed SKU. A measured result requires an uncancelled `line_verified` event AND a completed phase for the same person/work type in the valid attempt. A verification alone, cancelled/reopened work, unrelated site/order/SKU or another person's completion is insufficient. Use existing cancellation/parent-event semantics. Keep actual verifying/completing event IDs as evidence. If evidence is conflicting or does not cover the required quantity, show missing/needs review rather than guess. No months-wide scan: index/site-order lookup and bounded results.
4. Show `Framed by: Name ✓` with measured evidence, or `Framing scan missing` with a quick active same-site person picker. One selection can fill all missing framed SKUs, with per-line overrides if different people framed them; a compact chooser is enough. Persist this decision against the exact queued request/order/SKUs/person, never a mutable current-order singleton. Another scan cannot overwrite a blocked order or silently lose either job. Resolve one blocked job at a time; keep the other jobs in the existing queue.
5. Manual evidence is an assertion by the dispatcher. Save the chosen person's ID/name, recording actor, server record time, site/order/SKU and dispatch request/event. Do NOT insert a framing `line_verified`, `completed` or `started` event, fabricate durations, add framer KPI quantities, backdate a home department, or rewrite old events. Recheck measured evidence inside the dispatch transaction and prefer valid measured evidence that arrived before commit. If the manual person is no longer active/same-site, refuse with a clear reason.
6. Store immutable dispatch-time attribution rows (proposed `dispatch_framer_attributions`): one per dispatch event and framed SKU, with source `scan` or `manual`, bound person ID and display name, recorded_by/recorded_at, and measured event references where applicable. Uniqueness includes SKU (not only request ID). Match actual F6 receipt/event keys at implementation. RLS permits the existing report roles at allowed sites; kiosks use a narrowly scoped order RPC for needed evidence. No direct client insert/update/delete. Avoid a new editable attribution administration system.
7. Extend/reuse the F6 atomic save path for dispatch: authenticate caller/worker/badge/site, lock the same order, replay immutable request, reject existing/partial dispatch work, re-evaluate evidence, save dispatcher line verifications/dispatched event using existing routing/counting rules, deduct only components that belong at dispatch, apply F4 packaging, save attribution and receipt in one transaction. Existing A0 deductions/packaging must not be charged again at dispatch. Missing components or unresolved packaging block the whole transaction; retry never charges twice. Keep CS/replacement/cancelled/edited/truncated/unsupported orders in classic fallback. Don't invent new inferred item counts or F1/F8 timing semantics.
8. Awaiting a manual choice is definitively pre-commit, so it can update the prepared job through an explicit state transition. Once a commit has been attempted with unknown outcome, the request payload is frozen and only exact replay is permitted. Never mutate an uncertain request into a new request to evade its receipt. Account/site changes pause the old job instead of rebinding it.
9. Reports: show the stored framer attribution and clear `Manual` label in the existing per-order history/details; append straightforward CSV fields for framer names/evidence sources associated with dispatch rows. Batch by the displayed/exported event IDs within the existing site/date filter. Preserve event counts and existing columns. Manual attribution must not be counted as measured framing work. A small attribution list is enough; no F8 report redesign or fabricated performance chart. Use ordinary CSV escaping and protect spreadsheet formula prefixes for newly exported free-text names.

## Acceptance and operations

Focused checks: measured evidence requires completion; cancelled/cross-site/conflicting evidence is not accepted; per-SKU mixed evidence/manual labels; same-shift identity and expiry; no old-person job after async badge/site switch; multiple blocked jobs preserved; manual save and stock/packaging fail atomically; exact retry and two-device duplicate dispatch; actual role and RLS refusal; measured evidence arriving between picker and commit; Reports/CSV visibly distinguish manual attribution. Reuse F6 test helpers instead of another framework. One full gate and fresh focused branch review at the end.

Release on staging uses the next unused migration after F6, never edits installed F4/F5/F6 migrations. Previous app must still work on the expanded schema. Roll back by choosing classic mode/previous Preview; preserve receipts and immutable evidence. No external messages, Shopify writes, credentials, new dependencies or scheduled jobs. Document real scanner and packaging-rule commissioning separately, without claiming it was done overnight.

## Required F6 compatibility

- Current F6 uses `scanner_requests.kind` values `activate` and `commit`, a shared `(location, request_id)` key, and a unique saved framing commit per site/order. F7 must add a distinct dispatch kind and its own saved-dispatch uniqueness rule so a previously framed order can still be dispatched exactly once. Preserve F6 receipts and the framing index; installed 0055 must not be edited.
- F6 scanner events in one save share the original scan timestamp. Event IDs ending `-c-<work_type>` sort before `-vNN`; evidence resolution must not depend on lexicographic ordering of equal timestamps. Require compatible same-person verification/completion with completion time >= verification time and honor cancellations/attempt boundaries.
- Existing persisted outbox jobs are framing jobs. Default old rows to framing; retain the same scope key so existing queues remain visible. Delivery uses each job's captured mode, never the current screen mode. Use the reviewed F6 lease fencing, caller binding and unknown-outcome rules unchanged.
- Keep the classic/shared DB event guard phase-aware: a saved framing receipt must not prevent later dispatch, while duplicate framing credit remains blocked. Preserve explicit CS replacement paths.
- Reuse the reviewed F6 stock deduction helper and F4 packaging transaction. A separate compact dispatch RPC is acceptable; do not copy an inventory engine or generalize all production workflows.

## Evidence/report implementation anchors (read current code)

- Classic per-line unverify writes `cancelled.parent_event_id = line_verified.id`; whole-order scrap writes `cancelled` with null SKU/parent, while per-line mid-progress cancellation has a SKU. Use the actual rows, not the outdated comment claiming Reports tracks latestStart.
- `Reports.tsx:deriveCompletedLines` currently counts uncancelled line_verified events and gap-based timing; it does NOT require completion. F7 evidence needs its explicit stricter completed-phase check and must not alter existing report KPI math as a side effect.
- Existing `OrderLookupCard` inside Reports.tsx is the appropriate small per-order attribution display target. Existing handleExport supplies filtered raw events; batch attribution only for applicable dispatch IDs in that set and retain current event columns/counts.
